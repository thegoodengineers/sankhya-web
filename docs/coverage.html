Presolve done #43 landed six reductions (empty row, redundant row, fixed column, empty column, singleton row, forcing row); #92, merged as 780d7be, added the two it deferred, free-column-singleton and doubleton-equation elimination, with their dual reconstruction corrected in 1a60b9d. On by default, and postsolve re-measures the recovered point against the original model, so a wrong dual from a bad postsolve surfaces as a feasibility violation rather than as a quiet wrong answer - which is exactly the failure class this project is built to avoid. #412 lists what is still missing against a published presolve suite (duplicate rows and columns, dual fixing, dominated columns, implied free column substitution, binary probing, coefficient tightening); its first reduction, dual fixing (presolve_dual_fixing: a column whose entries can only push their rows away from a finite bound one way, and whose cost never rewards that way, is fixed at the other bound), is built, replayed as a column nonbasic at that bound, checked against the exact oracle on random LPs and MILPs, and off by default until the Netlib and MIPLIB re-runs on main say what it changes. Its second, parallel rows (presolve_parallel_rows: a row that is a scalar multiple of an earlier one folds its scaled bounds into that row and goes; postsolve hands the dual back to it when the bound that binds was its own, on either sign of the scale, and the same for a Farkas weight), is checked on hand cases for which row carries the dual and against the exact oracle on random LPs with deliberately duplicated rows; off by default for the same reason. The third, dominated columns (presolve_dominated_columns: two columns on the same rows, one at least as cheap and row by row at least as helpful, so activity moves from the dominated one onto the dominating one; the dominated column is fixed at its lower bound when the dominating one is unbounded above, the dominating one at its upper bound when the dominated one is unbounded below, with the integrality of the move checked), is built the same way, on identical row supports only, and off by default on the same terms. Implied-free column substitution (presolve_implied_free; Andersen and Andersen 1995, sec. 6) generalises the free-column singleton to a continuous column whose box is never binding, the bounds its one row's activity range puts on it lying inside the box, so the same substitution removes column and row and the recovered value is inside the box by construction; built the same way, the exact oracle the judge, and off by default on the same terms.

Multi-core parallelization done; tree-level parallelism (#222) landed in #403, default one thread #57 via #169: OpenMP over the column loops that dominate an iteration (pricing, pivot row), deterministic by construction - results are bit-identical at threads=1 and threads=8 on the seven of the eight largest Netlib instances that finish (bench/results/netlib-0cd08cf-threads1.csv / -threads8.csv); the eighth, dfl001, hits the time limit in both and got FEWER iterations with eight threads (31,256 against 32,739) - measured with NO speedup at Netlib scale, where an iteration is too short to amortize a fork. Off unless --option threads=N; the build flag is SANKHYA_WITH_OPENMP. This is parallelism WITHIN one node's LP iteration, not #222's ask: a worker-thread pool exploring different branch-and-bound NODES concurrently, sharing only the incumbent, the global bound and the node queue. Assessed and left open rather than attempted rushed: BranchAndBound (src/mip/branch_and_bound_internal.hpp) carries far more per-search mutable state than the issue's coarse design assumes - pseudocosts, the cut pool and cut-row ageing, the conflict store (#292), checkpoint/resume state, the solution pool - and #222 itself asks for ThreadSanitizer in CI specifically because a data race here "shows up as a wrong bound once a month, not as a crash". The Windows MSYS2 toolchain the team develops on cannot link ThreadSanitizer (the same gap #223 hit for ASan/UBSan; the Ubuntu CI can), so a same-day implementation could not have been verified locally by the tool the issue names as necessary, on numerical code where ENGINEERING_RULES.md is explicit that a wrong answer scores zero and a missing feature scores partial. Recommendation: implement per #222's own design (worker-owned engine and scratch model, one mutex-guarded queue, incumbent under a mutex or atomic, in-flight node count for termination, threads=1 default so no existing benchmark CSV changes) with a TSan job in CI as the gate, rather than merge it unverified. Engineering-track issue, not a PS requirement: #297

297 asks for a sweeping refactor of the solver dispatch layer into a pluggable

SolverEngine interface, with a 45-item Definition of Done spanning a capability model, a solver registry, checkpoint/warm-start/interrupt abstractions, thread-safety and memory- ownership documentation, and eight separate new test categories - explicitly across the whole of src/core, src/simplex, src/pdhg, src/ipm, src/qp, src/mip and the CLI/ Python surfaces, while everything currently on main keeps working and every existing benchmark CSV stays comparable.

That is real, valuable, multi-week architectural work, and several of the properties it asks for already exist piecemeal - solve() in src/core/solve.cpp is already a single dispatch point classifying LP/MILP/QP/MIQP and routing to one engine each; SolveControl (#223) is already a shared interrupt/progress abstraction every engine takes; ResourceLimits / StopController (#289) already unify resource-limit handling; checkpoint.{hpp,cpp} (#287) and solution_pool.{hpp,cpp} (#225) already exist as their own modules. What #297 asks for on top of that - a formal SolverEngine interface and registry, a capability model, and the remaining ~40 items - has not been attempted here: doing it correctly means touching every engine at once, and doing it under deadline pressure, in one session, without first breaking the whole thing into independently reviewable pieces, is exactly the trade ENGINEERING_RULES.md warns against (a wrong answer scores zero; a missing feature scores partial). Recommended next step, if this is picked back up: split the 45-item Definition of Done into a handful of independently landable PRs (interface + registry first, migrating one engine at a time behind it, with the existing dispatcher as the fallback until every engine has moved), each gated the normal way - build clean, full suite green, no benchmark CSV regression - rather than one PR that has to get all 45 right at once.

Status after #402 (2026-09-22): the interface, the capability model, the registry and the selector exist in src/solver_engine/, with every built-in engine wrapped over its existing solve_*() function, and solve() reads two things from them, the LP engine's name and its warm-start capability, through the same select_engine() rule table as before, so no numerical path changed and the demo and the Netlib small tier re-run identically. What it is not yet: a single place that decides, since the CLI's accepted-name list in src/util/options.cpp, the name-to-function branches in solve.cpp and the registry are three copies, the classifier exists twice, and engine::solve() in src/solver_engine/solver_engine_dispatch.cpp is a narrower entry point than solve() (no presolve, limits or polish; it does run the status guard). The remaining items of the Definition of Done stay open on #297.
