1. The red line

No source code from an optimization solver is copied, vendored, linked, or read. That list explicitly includes CBC, Clp, HiGHS, SCIP, SoPlex, GLPK, lp_solve, OSQP, PDLP, cuPDLP / cuPDLP-C / cuPDLPx, OR-Tools GLOP and CP-SAT, Gurobi, CPLEX and Xpress — not their simplex, not their cuts, not their MPS readers.

HiGHS appears in this project only as the comparison baseline in bench/runners/compare.py. It runs either as an externally installed command-line binary or, where none is present, through the highspy pip package in a separate Python process. It is never linked into SANKHYA, never a build dependency, and no part of its source informs ours. The comparison results are in docs/BENCHMARKS.md section 3.

2b. Toolchains this has been built and tested with

PS26119 asks for a foundation someone else can pick up, and "it builds here" is not that. These are the toolchains the evidence in docs/BENCHMARKS.md was actually produced with, and the ones CI exercises on every push. scripts/preflight.sh reports what it finds on the machine it runs on, and scripts/configure.sh chooses among them rather than trusting the order of PATH.

One toolchain must never be selected: a MinGW 6.3.0 that predates C++20 and sits on PATH on at least one development box. scripts/configure.sh rejects any g++ reporting a major version below 10, which is why it exists rather than the build simply calling cmake.

Third-party sources are pinned by tag in CMakeLists.txt, and docs/sbom.spdx.json - the SPDX 2.3 bill of materials - is generated from those pins by tools/make_sbom.py. CI runs tools/make_sbom.py --check, so a dependency added to the build without an entry in the table above turns the tree red instead of passing quietly.

31 NLP stage 1 (the .nl reader, the Hessian of the Lagrangian, the compiled tapes): what was read, given that the .nl format belongs to AMPL and the reference reader ships inside the AMPL/solver interface library, and that several NLP solvers read .nl files? Written from two documents only; no solver source read The reader is written from Gay's "Writing .nl Files" (SAND2005-7907P), a technical report describing the format for people writing it without AMPL, and the variable-ordering tables of Gay's "Hooking Your Solver to AMPL", a manual; both were read as PDFs from ampl.github.io. The AMPL/solver interface library (netlib ampl/solvers), which both documents point to as the reference implementation, was NOT read: it is an interface library rather than a solver, but it is distributed together with solver drivers, and the specification was sufficient. Three operator codes AMPL is known to emit (the specialised powers) are not in either document and are refused rather than guessed. No solver's .nl reader or NLP code was opened: not Ipopt, KNITRO, CONOPT, SNOPT, Bonmin, Couenne, BARON, filterSQP, SCIP, or any solver on the red line of section 1. The derivatives are written from Griewank & Walther and Walther (2008); no AD tool's source (ADOL-C, CppAD, CasADi) was read either, though none is a solver.
32 NLP stage 2 (the interior point, its tests): what was read, and where the Hock-Schittkowski problems come from? Written from the paper; test problems parsed from published AMPL models and written as .nl by Pyomo; HS book pages not cited The method is written from Wachter & Biegler (2006), a journal paper. The source of Ipopt - the paper's own implementation - was NOT read, nor that of KNITRO, CONOPT, SNOPT, Bonmin, Couenne, BARON, filterSQP, PIQP or any solver on the red line of section 1. The 70 Hock-Schittkowski problems in data/nlp/hs/ are Vanderbei's published AMPL transcriptions (vanderbei.princeton.edu/ampl/nlmodels/cute/, instance data with the published optimal objective, item 6 of the policy), PARSED by bench/runners/hs_mod_to_nl.py rather than retyped, and written as .nl by Pyomo 6.10.1 (a modeling language, not a solver; used at data-generation time only, never linked). The sha256 of every downloaded model is in data/nlp/hs/REFERENCE.csv. The HS book itself (Hock & Schittkowski, LNEMS 187, 1981) and Schittkowski's collection report could not be retrieved (every source returned 403), so reference values are cited by problem number and model file, NOT by book page; no page number was invented. The specialised power opcodes aside, Pyomo's .nl files use only operators the reader accepts.
33 NLP stage 3 (convex MINLP): what was read, and are MINLPLib's files usable as test data? Written from the papers; MINLPLib instances used as published data The method is written from Gupta & Ravindran (1985) and Dakin (1965). The source of Bonmin, Couenne, BARON, SCIP, DICOPT, Knitro's MINLP, or any solver on the red line was NOT read. Outer approximation (Duran & Grossmann 1986, Fletcher & Leyffer 1994; #528) is a different method and is not implemented here. MINLPLib's convexity flag is recorded but not relied on: the branch and bound runs only where this solver's own composition rules prove the relaxation convex.
